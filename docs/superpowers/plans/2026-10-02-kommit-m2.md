# kommit M2 Implementation Plan: consumer groups and idempotent producers

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (chosen) or superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Classic Kafka consumer groups and idempotent producers on top of the M1 broker, so that `kcat -G` and the Java client (console producer/consumer, `kafka-consumer-groups.sh`) work, and a group's lag is literally `git rev-list --count`.

**Architecture:** Committed offsets live in the partition logs: a `PartitionLog` commits and reads offsets for a group, and `GitLog` stores them as refs `refs/groups/<group>/<topic>/<partition>` pointing at first-parent position *c* (the sentinel for *c = 0*). A new `groups::Coordinator` runs the classic group state machine in memory (`Empty → PreparingRebalance → CompletingRebalance → Stable`), with a ticker task for session expiry and rebalance deadlines. Producer ids are allocated in blocks recorded as `AllocateProducerIds` metadata events. Idempotent batches are de-duplicated in memory per (producer id, topic, partition).

**Tech Stack:** as M1 (Rust, tokio, kafka-protocol 0.18 with `messages_enums`, gix 0.88). Tests: tokio paused time for the state machine; `kcat -G` and the `apache/kafka` Docker image for real clients.

**Spec:** `docs/superpowers/specs/2026-10-02-kommit-design.md` §6 (and §8, §9 for errors and tests).

## Global Constraints

- Everything from the M1 plan's Global Constraints still holds: pure-Rust broker, Git is the only source of truth, `fsck --strict` clean, real Kafka error codes, fmt/clippy clean, Conventional Commits on `main`, push after every task.
- `ApiVersions` advertises exactly what is implemented. M2 ranges:
  - FindCoordinator 0–6
  - JoinGroup 0–9
  - SyncGroup 0–5
  - Heartbeat 0–4
  - LeaveGroup 0–5
  - OffsetCommit 2–9
  - OffsetFetch 1–9
  - ListGroups 0–5
  - DescribeGroups 0–6
  - InitProducerId 0–6

  OffsetCommit and OffsetFetch v10 are topic-id only, so they are not advertised.
- **Every response field must be valid for the negotiated version.** `tests/versions.rs` is extended to cover every new API at every advertised version, and both success and error paths are exercised for the coordinator APIs.
- Committed offset *c* means "next record to read". It is stored as a ref at first-parent position *c* of the partition branch. `git rev-list --count refs/groups/<g>/<t>/<p>..<t>/<p>` must equal `high_watermark - c`, and a test asserts this with the real git CLI.
- **Group ids in refs:** a group id that passes `validate_topic_name` is used raw. Any other group id is encoded as `%` + lowercase hex of its UTF-8 bytes. `%` cannot occur in a valid Kafka topic-style name, so the two forms never collide, and Git allows `%` in ref names.
- Group membership is not persisted. After a restart, groups that have committed-offset refs reappear as `Empty`.
- Transactions are out of scope. `InitProducerId` with a non-null `transactional_id` returns `UNSUPPORTED_VERSION`, which the Java client reports as "transactions not supported".
- Static membership (`group.instance.id`) and the KIP-848 protocol are out of scope. `group_instance_id` is ignored.

## Spec deviations decided while planning

- **JoinGroup member ids:** JoinGroup v4+ does not use the `MEMBER_ID_REQUIRED` two-step. The broker assigns a member id on the first join and completes it, which current clients accept. This is simpler, and nothing in the spec depends on the two-step.
- **Initial rebalance delay:** the broker waits `group_initial_rebalance_delay` (default 300 ms, configurable; Kafka uses 3 s) when a group goes from Empty to its first rebalance. Members that start together then land in one generation instead of rebalancing twice.
- **Producer id blocks:** producer ids are allocated in blocks of 1000 via `MetaEvent::AllocateProducerIds { up_to }`. Startup resumes after the highest `up_to`.
- **Idempotent produce dedup:** the broker keeps the last 5 batches per (producer id, topic, partition): first sequence, last sequence and base offset. A batch whose first sequence matches a cached batch returns that batch's base offset without appending (Kafka's behaviour). A gap returns `OUT_OF_ORDER_SEQUENCE_NUMBER`. An unknown producer state (for example after a restart) accepts any first sequence. Kafka persists this state; kommit's lenience is documented.
- **Group-less commits:** an OffsetCommit with `generation_id = -1` (simple consumers) is accepted for any group without a membership check.

## Review Focus

1. **Group ids that are not ref-safe** (`my group`, `a..b`, `über`, empty string) must commit and fetch offsets and stay `fsck`-clean. The `%hex` encoding is pinned in Task 1.
2. **Committing an offset beyond the high watermark** (Kafka allows it; Git cannot point past the branch head) must return a clear error, not panic or corrupt anything. Kommit returns `OFFSET_OUT_OF_RANGE` for that partition. Pinned in Task 1.
3. **A member that stops heartbeating** must be evicted after its session timeout, and the survivors must rebalance and get its partitions. Otherwise the group stalls forever. Pinned in Task 4 with paused time.
4. **A JoinGroup or SyncGroup at an older version** (v0 has no rebalance timeout; v5 SyncGroup echoes protocol type and name) must encode correctly. Pinned in Task 8 (`versions.rs`).
5. **A retried idempotent batch** (same producer id and sequence) must not be stored twice. Pinned in Task 7.

### Task 1: Committed offsets in the partition logs

**Interfaces produced:**
- `PartitionLog::commit_offset(&self, group: &str, offset: Offset) -> Result<(), LogError>`: `offset` must be in `0..=hw`, otherwise `OutOfRange`.
- `PartitionLog::committed_offset(&self, group: &str) -> Result<Option<Offset>, LogError>`
- `groups::group_ref_component(group: &str) -> String`: the raw name, or `%` + hex.
- `log::git::group_ref(group, topic, partition) -> String`, which returns `refs/groups/<component>/<topic>/<partition>`.
- `GitStore::refs_with_prefix(&self, prefix: &str) -> anyhow::Result<Vec<(String, ObjectId)>>`

**Behaviour:**
- **GitLog commit:** moves the group ref to `index[offset]` with `PreviousValue::Any`, because offsets may move backwards on purpose (reset).
- **GitLog read:** resolves the ref target's position by searching the index from the end. A ref that points outside the partition's chain is treated as "no committed offset", with a warning.
- **MemLog:** a `HashMap<String, Offset>`.

**Tests (contract plus Git-specific):**
- The contract gains: no commit gives `None`; commit 0 then 2 reads back 2; committing `hw + 1` gives `OutOfRange`; committing back to 0 is allowed.
- GitLog: after committing *c*, `git rev-list --count <groupref>..orders/0` equals `hw - c`; the value survives a reopen; group ids `my group`, `a..b` and `über` round-trip and `fsck --strict` stays clean.
- `group_ref_component` unit tests cover the raw and `%hex` forms.

### Task 2: Storage load and producer id blocks

**Interfaces:**
- `MetaEvent::AllocateProducerIds { up_to: i64 }`
- `Storage::load(&self) -> Result<Loaded>`, replacing `load_topics`. It returns `Loaded { topics: Vec<LoadedTopic>, groups: Vec<String>, producer_id_high: i64 }`. `groups` holds the decoded group ids found under `refs/groups/`.
- `Storage::allocate_producer_ids(&self, up_to: i64) -> Result<()>`
- `producers::ProducerIds::next(&self, storage) -> Result<i64>`: hands out ids from the current block and records a new block of 1000 when it runs out. Ids start at 0.
- `Broker::next_producer_id()`
- `Broker::known_groups()`, which seeds the coordinator.

**Tests:**
- Two brokers on the same repo, sequentially: the ids the second hands out are greater than every id the first handed out.
- `MetaEvent` TOML round-trip.
- Groups with committed offsets are listed after a restart.

### Task 3: FindCoordinator, OffsetCommit, OffsetFetch, and request context

- **RequestContext:** `dispatch` takes a `RequestContext { client_id, client_host }`. The server fills `client_host` from the peer address as `/ip`, like Kafka.
- **FindCoordinator:**
  - v0–3 answer with the single `node_id`/`host`/`port`; v4–6 return `coordinators[]`, one per key.
  - `key_type` 1 (transactions) gets `COORDINATOR_NOT_AVAILABLE`.
- **OffsetCommit:**
  - Every partition goes through `commit_offset`.
  - If the group is known to the coordinator and `generation_id >= 0`, the member and generation are validated: `UNKNOWN_MEMBER_ID` or `ILLEGAL_GENERATION` is returned for every partition.
  - `generation_id = -1` is accepted unchecked. An unknown topic or partition gets `UNKNOWN_TOPIC_OR_PARTITION`.
- **OffsetFetch:**
  - v1–7 use the single-group shape; v8–9 use `groups[]`.
  - `topics = None` means every partition with a committed offset for the group.
  - A missing offset returns `committed_offset = -1`, metadata `""`, and no error.

**Tests (wire):**
- A commit/fetch round trip.
- Fetching all topics.
- An unknown member with `generation >= 0` on a live group is rejected.
- A missing offset returns -1.

### Task 4: Group coordinator state machine (unit tests with paused time)

`Coordinator` exposes async calls, each returning the response values (not wire structs):
- `join(group, member_id, client_id, client_host, session_timeout, rebalance_timeout, protocol_type, protocols) -> JoinOutcome`
- `sync(group, generation, member_id, assignments) -> SyncOutcome`
- `heartbeat(group, generation, member_id) -> Result<(), CoordError>`
- `leave(group, member_ids) -> Vec<(member_id, Result<(), CoordError>)>`
- `validate_commit(group, generation, member_id) -> Result<(), CoordError>`
- `list() -> Vec<(group, state, protocol_type)>`
- `describe(group) -> Option<GroupView>`

**Rules:**
- **Join:**
  - An empty member id gets a new id, `<client_id>-<uuid>`. An unknown non-empty id gets `UNKNOWN_MEMBER_ID`.
  - A member whose protocol type differs from the group's, or with no protocol in common with the group, gets `INCONSISTENT_GROUP_PROTOCOL`.
  - Joining puts the group into `PreparingRebalance`, unless it is already there. The deadline is now + the longest member rebalance timeout. For a group coming from Empty, it is now + `initial_delay` instead (and that delay is not extended).
  - The join completes when every current member has joined this round (and, from Empty, the initial delay has passed), or when the deadline passes.
  - **On completion:**
    - Members that did not rejoin are removed and the generation is incremented.
    - The protocol is the leader's first preference that every member supports.
    - The leader is the previous leader if it is still a member, otherwise the first member to join.
    - The leader receives every member's metadata; the others receive an empty list.
    - The group moves to `CompletingRebalance`, or to `Empty` if no members remain.
- **Sync:**
  - An unknown member gets `UNKNOWN_MEMBER_ID`; a wrong generation gets `ILLEGAL_GENERATION`; during `PreparingRebalance`, `REBALANCE_IN_PROGRESS`.
  - In `CompletingRebalance`, the leader's sync stores the assignments, moves the group to `Stable`, and answers every parked follower. A follower's sync is parked until then.
  - In `Stable`, a sync answers with the stored assignment immediately.
- **Heartbeat:** errors as for sync; during `PreparingRebalance` it returns `REBALANCE_IN_PROGRESS`. Otherwise it refreshes the member's last-seen time. Join and sync also refresh it.
- **Leave:** removes the member. If the group is now empty it becomes `Empty` (the generation is kept); otherwise a rebalance starts.
- **Ticker:** every 50 ms, members past their session timeout are expired and a rebalance starts; deadlines due are completed. A parked join of an evicted member is answered `UNKNOWN_MEMBER_ID`.

**Unit tests (paused time):**
- A single member joins and becomes leader of generation 1; a sync returns its own assignment.
- Two members join within the initial delay and get one generation; the leader sees both sets of metadata, and the follower's parked sync is released by the leader's sync.
- A third member joining a Stable group makes heartbeats return `REBALANCE_IN_PROGRESS`; once everyone rejoins, the generation advances.
- **Session expiry (Review Focus 3):** a member stops heartbeating, is expired, and the survivor rejoins as the sole member and leader.
- Leave by the leader means the remaining member becomes leader after rejoining.
- Errors: wrong generation, unknown member, inconsistent protocol.

### Task 5: JoinGroup, SyncGroup, Heartbeat, LeaveGroup handlers

These are thin wire adapters over the coordinator:
- `protocol_type` and `protocol_name` are set on responses only at the versions that carry them: JoinGroup protocol type v7+, SyncGroup protocol type and name v5.
- LeaveGroup v0–2 uses `member_id`; v3+ uses `members[]` with per-member errors.
- JoinGroup `rebalance_timeout_ms` defaults to `session_timeout_ms` for v0.

**Wire test:** two TestClients join the same group concurrently and get the same generation and one leader. The leader syncs an assignment, the follower receives its share, both heartbeat cleanly, then the leader leaves and the follower's heartbeat gets `REBALANCE_IN_PROGRESS`.

### Task 6: ListGroups and DescribeGroups

- **ListGroups:** returns every group the coordinator knows, including Empty groups that only have offsets. `group_state` is set for v4+ and `group_type` (`"classic"`) for v5.
- **DescribeGroups:**
  - `group_state` uses Kafka's strings: `Empty`, `PreparingRebalance`, `CompletingRebalance`, `Stable`, `Dead`. `protocol_type` and `protocol_data` (the protocol name) come from the group.
  - Members carry their metadata for the chosen protocol and their assignment.
  - An unknown group answers `Dead` with no error, as Kafka does.

**Wire tests:** after the Task 5 flow, both APIs show the group as Stable with two members. After a restart with committed offsets, the group is listed as Empty.

### Task 7: InitProducerId and idempotent produce

- **InitProducerId:** returns a fresh id from `Broker::next_producer_id()` with epoch 0. A non-null `transactional_id` returns `UNSUPPORTED_VERSION`.
- **Batch decoding:** `records::decode_produce_batches(bytes) -> Vec<ProducedBatch { producer_id, producer_epoch, first_sequence, records }>` keeps batch boundaries. Produce appends batch by batch.
- **Dedup:** a batch with `producer_id >= 0` goes through `IdempotenceCache::check_and_record(pid, topic, partition, first_seq, last_seq, append)`. That holds a mutex across the append, so a check-then-append cannot race. Outcomes:
  - **Duplicate:** returns the cached base offset.
  - **Gap:** returns `OUT_OF_ORDER_SEQUENCE_NUMBER`.
  - **New:** appends and caches.

**Wire tests:**
- A batch with pid 7, sequences 0–1, sent twice: the high watermark stays 2 and both answers have base offset 0.
- Then a batch with sequence 5 gets `OUT_OF_ORDER_SEQUENCE_NUMBER`.
- InitProducerId with a transactional id is refused.
